# AGENTS.md

## Жёсткое правило: каждый change проходит ревью

**Любое изменение кода (любой файл, любой язык) обязано пройти ревью строгим ревьюером до того, как задача считается готовой.** Это распространяется на все сессии Claude Code и все субагенты в этом репозитории.

### Порядок

1. Внести изменения.
2. Запустить ревью изменённого кода (diff vs `HEAD`, либо конкретные файлы) строгим ревьюером — отдельным агентом с установкой «находи всё: баги, гонки, безопасность, регрессии, нарушение конвенций репозитория», а не мягким просмотром.
3. Все подтверждённые замечания (correctness, concurrency, security, сломанные контракты API) — **исправить обязательно**. Спорные/косметические — зафиксировать в ответе пользователю.
4. Пересобрать/прогнать тесты (`./mvnw -T 2C test -Pfast -q`, при фронте — `pnpm lint && pnpm test`).
5. Только после чистой итерации ревью задача считается завершённой.

### Минимальные критерии «строгого» ревьюера

- проверяет конкурентность (общий мутабельный state, видимость, атомарность);
- проверяет границы и валидацию входных данных;
- проверяет сохранение существующих контрактов (REST-формы, сериализация, кэш);
- ищет регрессии в затронутых вызывающих местах;
- не принимает «выглядит правильно» без прогона тестов.

### Запреты

- Не считать изменение готовым без шагов 2–5.
- Не отменять ревью из-за «маленькой правки» — размер не имеет значения.

## Жёсткое правило: коммиты — маленькие срезы, хорошо описанные

**Запрещено копить большой объём изменений одним коммитом (или одним незакоммиченным «куском» в рабочем дереве).** Коммит — это один логический срез: одна причина изменения, понятная без чтения диффа.

### Порядок

1. Любая работа делится на последовательность маленьких самодостаточных срезов (например: «DDL + модель», «репозиторий», «REST», «форма в UI», «локализация», «док» — каждый своим коммитом).
2. Каждый срез проходит ревью (правило выше) и тесты — и **сразу коммитится**, не дожидаясь остальных. Каждый коммит в отдельности должен собираться и держать тесты зелёными.
3. Сообщение коммита описывает **зачем** и **что**, а не только где: повелительная строка ≤ 72 символов (feat/fix/refactor/docs/test/chore — как в истории репозитория), затем тело с контекстом и ссылкой на связанную задачу. Читатель должен понять смысл коммита, не открывая дифф.
4. В одном коммите не смешивать: код и механическое переформатирование; фичу и починку несвязанного; генерируемые артефакты и исходники (кроме случаев, когда сборка требует их в репозитории).

### Запреты

- Не делать один коммит на «целую фичу» — резать до срезов.
- Не копить незакоммиченные изменения через несколько задач: рабочее дерево между задачами должно быть чистым.
- Не писать сообщения вида «fix», «update», «wip» — если не формулируется зачем, срез слишком крупный или слишком мелкий.
